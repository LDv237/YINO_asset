# 复现入口

这份文件把“下载哪个文件、解压到哪里、依次执行哪几条命令”写死，避免只拿分类附件时因为缺少 `derived/` 或 `raw/` 而无法校验。

历史正式基准：`20261020T072820Z-53b5`（抽象做市 / interval，388,394 条 WAL，10,131 fills）。最终代码单源 run：`20261021T033309Z-4ac9`（178,954 帧，4,908 fills，queue/durable 字段完整），单独放在 `07_最终代码单源复跑/`。

## 方式 A：完整 Release 运行目录（推荐）

这是最省事、最完整的路径，`raw/`、`derived/`、`config/summary/manifest` 和 `replay/` 都已经在包里。

1. 下载并解压 Release 里的 `YINO_artifacts_complete_20261020.zip`：

   https://github.com/LDv237/YINO_asset/releases/download/delivery-20261020/YINO_artifacts_complete_20261020.zip

   解压后得到 `artifacts/`，里面包含 `artifacts/runs/20261020T072820Z-53b5/`。

2. 下载代码包 `YINO_delivery_complete_20261020.zip`（或仓库源码），解压后安装依赖：

   ```bash
   python -m pip install -r requirements-lock.txt
   ```

3. 在包含 `artifacts/` 的目录下执行：

   ```bash
   python -m tickforge verify --run artifacts/runs/20261020T072820Z-53b5
   python -m tickforge replay --run artifacts/runs/20261020T072820Z-53b5 \
     --out artifacts/runs/20261020T072820Z-53b5-replay --verify
   ```

   预期：`verify` 输出 `"ok": true`；`replay --verify` 输出 `verified=true`、`deterministic=true`，三个 SHA-256 一致。

### 方式 A2：最终代码单源 run

如果想验证最终代码的 15 分钟单源 run（日志、信号、成交、性能和回放来自同一次运行），直接重建 `07_最终代码单源复跑/`：

```bash
python scripts/reproduce_from_delivery.py \
  --delivery 交付材料/07_最终代码单源复跑
```

或者从完整 Release 的 `artifacts/runs/20261021T033309Z-4ac9/` 直接执行 `verify` 和 `replay --verify`。

## 方式 B：只有邮件附件/分类材料

`交付材料/02_正式运行/` 为了控制邮件体积，把 WAL 和 derived 都做成了压缩包，所以它本身不是 `tickforge verify` 能直接读的 run 目录。已经额外放了 `derived.tar.gz`，可以完整重建：

```bash
# 在含 交付材料/、scripts/、tickforge/ 的包根目录执行
python -m pip install -r requirements-lock.txt
python scripts/reproduce_from_delivery.py
```

脚本会依次做四步：

1. 解压 `交付材料/02_正式运行/原始WAL.tar.gz` 到临时 run 目录的 `raw/`；
2. 解压 `交付材料/02_正式运行/derived.tar.gz` 到 `derived/`；
3. 复制 `config.json`、`正式运行摘要.json -> summary.json`、`正式运行清单.json -> manifest.json`；
4. 执行 `verify` 和 `replay --verify`。

默认临时目录是 `artifacts/reproduced/20261020T072820Z-53b5`，可以用 `--workdir` 指定别的位置。手工等价命令：

```bash
RUN=artifacts/reproduced/20261020T072820Z-53b5
mkdir -p "$RUN"
tar -xzf 交付材料/02_正式运行/原始WAL.tar.gz -C "$RUN"
tar -xzf 交付材料/02_正式运行/derived.tar.gz -C "$RUN"
cp 交付材料/02_正式运行/config.json "$RUN/config.json"
cp 交付材料/02_正式运行/正式运行摘要.json "$RUN/summary.json"
cp 交付材料/02_正式运行/正式运行清单.json "$RUN/manifest.json"
python -m tickforge verify --run "$RUN"
python -m tickforge replay --run "$RUN" --out "$RUN-replay" --verify
```

如果只拿 `交付材料/02_正式运行/` 而不解压这两个压缩包，`verify` 会因为缺少 `raw/` 和 `derived/` 失败；这不是数据缺失，是分类附件为了体积做的拆分。

## 同步与完整性边界

正式基准 `53b5` 用 `fsync_policy=interval`：每 250 ms **尝试**组提交，正常关闭会排空队列并 flush+fsync，实测 `lost_raw_frames=0`、`drained=true`。进程崩溃或掉电时，未同步的 WAL 尾部可能丢失；250 ms 是目标间隔，不是硬上界。这不是运行期静默丢帧。

严格落盘版 `6db8` 用 `always`：每条记录 fsync 后才处理，属于应用层保证，不等于物理介质绝对安全；那次运行有 2 次网络重连、12 次 resync 和 1,379 个缺失 aggTrade ID，是网络/积压窗口下的已知代价，不影响 `interval` 版 53b5 已经完成的链路。

更完整的延迟、资源和 fsync 对照见 `docs/性能实测.md`。
