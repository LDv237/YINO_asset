# 开发过程与试错记录

本文记录 TickForge 从最小链路到可回放系统的方案演进、遇到的问题和验证方法。

## 1. 起点：先跑通最小链路

最初目标是尽快确认“行情能进来、能落盘、能出信号”，所以先从单交易对、`@aggTrade` 单流开始，验证连接、消息解析、WAL 写入和派生输出。这个阶段不追求复杂策略，只确认链路是通的。

基础链路确认后，再逐步加入：

- `depth@100ms` 全深度订单簿；
- `bookTicker` 最优档；
- 6 个 USDT 交易对，提高 15 分钟窗口的负载；
- 因子、做市信号、模拟成交；
- 健康检查、Prometheus 指标和确定性回放。

## 2. 先冻结接口，再写实现

在扩大功能前，我先把事件结构、WAL 二进制格式、模块签名、指标名、确定性与不丢数据的约束写成 `docs/接口设计.md`。这样后续存储、订单簿、因子、策略/执行、接入、指标可以分开实现，再按同一个契约集成。

这一步的收益是：每个模块可以先独立测试，不需要等整条链路完成；出现问题时也能判断是实现偏离了契约，还是契约本身需要调整。

## 3. 遇到的问题与修正

### 3.1 主站不可达

最初直连 `stream.binance.com`，连接失败。探测多个域名后确认 `data-stream.binance.vision` 可用，于是改为币安行情专用只读域名；这不是换数据源，而是同一交易所的公开行情入口。先把网络环境排除，再排查代码。

### 3.2 双生产者顺序竞态

早期设计里，快照任务和 WebSocket 回调都可能分配 `seq`、写入 WAL 并进入处理队列；队列满时，先分配序号的协程可能后入队，导致 WAL 物理顺序与处理顺序不一致。

修正为：

- 单一 ingestion 锁串行化 socket 与快照两个生产者；
- `seq` 在 WAL append 前分配；
- 队列满时等待/反压，不丢弃已持久化事件；
- 增加“WAL 顺序 = 处理顺序”的测试，并在回放中校验摘要。

### 3.3 重连时的隐式状态重置

早期实现会在 WebSocket 重连时清空所有订单簿和缓冲，然后请求新快照。这个状态转移没有写入 WAL，回放时不会发生，因此 live 与 replay 可能不一致。

修正为：重连只记录 data gap，是否重建订单簿由下一笔 depth 的 `U/u` 连续性决定。没有丢包时订单簿可以无缝续用；有丢包时自然进入缓冲和快照恢复。这样 live 与 replay 使用同一套状态机。

### 3.4 fsync 测试竞态

测试曾在第一次定时 fsync 后就断言 10 条记录全部 durable，但此时 writer 仍在排队。修正为等待写入序号 + 显式 `flush_and_sync()` 屏障，避免把测试调度误判为实现问题。

### 3.5 OFI 符号方向

用独立参考模型对照时发现，ask 侧价格变化符号与经典 Cont–Kukanov–Stoikov 定义相反：ask 下移被记为正，而实现时的测试把同一错误方向写成了期望值。

修正为：ask 下移 `-cur_qty`、ask 上移 `+prev_qty`，同时修改接口文档、实现注释和测试。这个错误说明“测试全绿”不等于“规格正确”，必须有独立对照。

### 3.6 tick 精度

手写测试的期望值多加了三位零，被 `str_to_ticks` 的边界测试立即抓住。这类错误如果只靠人眼检查很容易漏，所以价格/数量的整数 tick 转换必须有独立用例。

### 3.7 旧快照回退订单簿

REST 快照可能在较新的 depth 增量之后才完成并入队；旧实现会用较老的 `lastUpdateId` 重建订单簿，下一笔连续增量就被误判为 gap。

修正为：`apply_snapshot` 拒绝 `lastUpdateId < current_last_update_id`，不重建、不回退；新增回归测试。

### 3.8 严格落盘下的代价

`fsync_policy=always` 每条记录 fsync 后才处理，15 分钟运行只有约 27 万帧，p50 约 3.4ms，明显慢于 interval 模式；期间还遇到 2 次网络重连。这个实验说明持久化语义必须和性能指标一起报告，不能只写“零丢失”。

## 4. 验证方法

1. **接口对照**：每个模块按 `docs/接口设计.md` 的签名和状态语义检查。
2. **单元测试**：订单簿序列/随机对拍、WAL 轮转/CRC/截断、因子手算、策略与模拟执行、指标并发。
3. **集成测试**：本地模拟 WebSocket + REST，跑完整链路、优雅关停、WAL 校验和回放。
4. **真实行情 smoke**：短时间连接 Binance，检查解析、快照、订单簿同步和健康检查。
5. **15 分钟实测**：检查丢失、队列排空、延迟分位、重连/快照计数和资源。
6. **回放摘要**：同一 WAL 回放后，因子/信号/成交三个 SHA-256 与实时一致才算复现成功。
7. **异常终止实验**：强制终止进程后检查已 fsync 的 WAL 前缀可读、CRC/seq 有效。

## 5. 反思

对“测试通过”保持警惕：测试只证明它检查过的内容，不能替代规格对照、真实行情和回放摘要。对“零丢失”也要拆开口径：正常关闭、进程崩溃、物理掉电是三种不同场景，报告里必须分别说明。
