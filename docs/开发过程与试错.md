# 开发过程与试错记录

这篇按时间顺序记 TickForge 从最小链路做到可回放系统的过程，重点写当时卡在哪儿、后来怎么改，验证方法放在后面。

## 1. 起点：先跑通最小链路

最初的目标很直接：尽快确认三件事，行情能进来、能落盘、能出信号。所以先从单交易对、`@aggTrade` 单流开始，把连接、消息解析、WAL 写入和派生输出跑通。这个阶段不碰复杂策略，只看链路通不通。

链路通了以后，功能一块一块往上加：`depth@100ms` 的全量订单簿、`bookTicker` 最优档、6 个 USDT 交易对（把 15 分钟窗口的负载提上来）、因子和做市信号、模拟成交，再往后是健康检查、Prometheus 指标和确定性回放。

## 2. 先冻结接口，再写实现

在扩大功能之前，我先把事件结构、WAL 二进制格式、模块签名、指标名，还有确定性和不丢数据这两条约束，写进了 `docs/接口设计.md`。这样后面存储、订单簿、因子、策略/执行、接入、指标可以分开写，再按同一份契约拼起来。

好处很直接：每个模块能先单独测，不用等整条链路；出了问题也容易判断，到底是实现偏离了契约，还是契约本身要改。

## 3. 遇到的问题与修正

按时间顺序，主要的坑是下面这些。

### 3.1 主站不可达

最早我直连 `stream.binance.com`，连接失败。我先把网络环境排除，探了几个域名，确认 `data-stream.binance.vision` 可用，就换成了币安行情专用的只读域名；这不是换数据源，还是同一家交易所的公开行情入口。网络排除掉之后，才回去看代码。

### 3.2 双生产者顺序竞态

早期设计里，快照任务和 WebSocket 回调都能分配 `seq`、写 WAL、进处理队列。队列一满，先分到序号的协程可能后入队，WAL 的物理顺序和处理顺序就对不上了。

改法是加一把单一的 ingestion 锁，把 socket 和快照这两个生产者串起来；`seq` 统一在 WAL append 之前分配；队列满了就等待、反压，已经持久化的事件不能丢。另外补了一个“WAL 顺序等于处理顺序”的测试，回放时也校验摘要。

### 3.3 重连时的隐式状态重置

早期版本在 WebSocket 重连时会把所有订单簿和缓冲清空，再请求新快照。问题是这个状态转移没写进 WAL，回放时不会发生，live 和 replay 就可能对不上。

后来改成：重连只记一个 data gap，订单簿要不要重建，交给下一笔 depth 的 `U/u` 连续性来判断。没丢包就接着用，丢了就自然进缓冲、走快照恢复。这样 live 和 replay 走的是同一套状态机。

### 3.4 fsync 测试竞态

有个测试曾经在第一次定时 fsync 之后就断言 10 条记录全部 durable，其实那时候 writer 还在排队。后来改成等写入序号，再加一个显式的 `flush_and_sync()` 屏障。这样就不会把测试自己的调度问题当成实现的问题。

### 3.5 OFI 符号方向

用独立参考模型对照的时候发现，ask 侧价格变化的符号跟经典 Cont–Kukanov–Stoikov 的定义是反的：ask 下移被记成了正。更麻烦的是，实现时的测试把这个错误方向也写成了期望值，所以测试一直是绿的。

改法是 ask 下移记 `-cur_qty`、上移记 `+prev_qty`，接口文档、实现注释和测试一起改。这个坑让我记住一件事：测试全绿不代表规格是对的，必须有独立对照。

### 3.6 tick 精度

手写测试的期望值多加了三位零，被 `str_to_ticks` 的边界测试当场抓住。这种错人眼很难看出来，所以价格和数量的整数 tick 转换必须有独立用例。

### 3.7 旧快照回退订单簿

REST 快照有可能在较新的 depth 增量之后才完成、才入队。旧实现会拿这个较老的 `lastUpdateId` 去重建订单簿，结果下一笔本来连续的增量被误判成 gap。

改法是 `apply_snapshot` 直接拒绝 `lastUpdateId < current_last_update_id` 的快照，不重建、不回退，再补一个回归测试。

### 3.8 严格落盘模式实测

`fsync_policy=always` 是每条记录 fsync 完才处理。15 分钟只跑下来约 27 万帧，p50 大约 3.4 ms，比 interval 模式慢不少；该次严格模式运行还观察到 2 次网络重连，具体原因尚未隔离，不能唯一归因到 fsync。这个实验让我确定，持久化语义必须跟性能指标一起报，不能只写一句“零丢失”。

## 4. 验证方法

验证是分层做的。最前面是接口对照，每个模块按 `docs/接口设计.md` 的签名和状态语义检查一遍。然后是单元测试，覆盖订单簿序列和随机对拍、WAL 轮转/CRC/截断、因子手算、策略与模拟执行、指标并发。集成测试在本地起模拟的 WebSocket 和 REST，完整链路、优雅关停、WAL 校验、回放一起跑。再往外是真实行情 smoke，短时间连 Binance，看解析、快照、订单簿同步和健康检查。

15 分钟实测看的是丢失、队列排空、延迟分位、重连和快照计数、资源占用。回放摘要要求同一份 WAL 回放后，因子、信号、成交三个 SHA-256 都和运行目录里的 derived 一致，才算复现成功；交付 run 的 derived 已按统一执行口径从 WAL 重算。异常终止实验则是强制杀进程，恢复读取 WAL 可读前缀（229 条有效记录），检查 CRC 和 seq 是否有效；该证据不证明这 229 条都已完成 fsync。

## 5. 反思

做完这一轮，我对“测试通过”这四个字比以前谨慎。测试只能证明它检查过的东西，替代不了规格对照，也替代不了真实行情和回放摘要。对“零丢失”也一样，得先问是哪种场景：正常关闭、进程崩溃、物理掉电，三者的保证不是一回事，报告里必须分开写。
