# 正确性与可靠性验证

我把“能跑”拆成了六类可以重复的验证：单元正确性、状态机恢复、端到端链路、故障注入、确定性回放、完整性校验。下面所有命令都在项目根目录执行。

## 1. 验证矩阵

每一层看什么、证据在哪儿，都在这张表里。

| 层次 | 关注点 | 证据 |
|---|---|---|
| 单元测试 | 订单簿序列规则、WAL 格式/CRC、因子手算、策略风控、模拟撮合、指标并发 | `pytest` |
| 集成测试 | 本地模拟交易所（WebSocket + REST）→ 实时引擎 → WAL → 派生输出 → 回放 | `tests/test_integration_live.py` |
| 故障注入 | 断线重连、消息超时、REST 500/重试、WAL CRC 翻转、尾部截断、快照过旧/丢包、交叉簿 | 各模块测试中的 mock/fixture |
| 运行时对账 | 接收帧数 = WAL 记录数 = 已处理事件数；队列排空；无静默丢弃 | `summary.json.reconciliation` |
| 确定性回放 | 同一 WAL 回放产生的因子/信号/成交 SHA-256 与运行目录 derived 一致（历史 run 的 derived 为同口径重算；最终单源 run 为 live 同源） | `replay_summary.json.comparison` |
| 完整性校验 | WAL magic/长度/CRC/seq、manifest 分段 SHA-256、derived 重算、产物校验和 | `python -m tickforge verify` |

## 3. 15 分钟实测的对账口径

`summary.json` 里是这么几组字段：

```json
{
  "counts": {"ws_frames_received": ..., "processed_envelopes": ...,
             "pipeline": {"ws_frames": ..., "snapshots": ..., "factor_snapshots": ...,
                          "signals": ..., "fills": ...}},
  "wal": {"records_ws": ..., "records_snapshot": ..., "records_total": ...},
  "reconciliation": {"lost_raw_frames": 0, "unprocessed_at_shutdown": 0,
                     "not_enqueued_at_shutdown": 0, "drained": true},
  "derived_complete": true,
  "derived_errors": {},
  "clean_shutdown": true
}
```

判定就按这六条来：

1. `ws_frames_received == wal.records_ws`：每个收到的原始帧都进了 WAL（正常关闭时 flush+fsync；`interval` 的崩溃窗口见 `docs/性能实测.md` 第 4 节的持久化契约）；
2. `wal.records_ws + wal.records_snapshot == processed_envelopes`：每个持久化事件都被处理；
3. `lost_raw_frames == 0`、`unprocessed_at_shutdown == 0`、`not_enqueued_at_shutdown == 0`；
4. `clean_shutdown == true`，且 `derived_complete == true`：三个派生文件都成功 flush/close 并生成 SHA-256；任一 `sink.close()` 失败会写进 `derived_errors`，同时把 `clean_shutdown` 置为 false；
5. `verify` 通过；
6. `replay --verify` 的 `digests` 三项全部匹配。

统计窗口从第一条行情到达才开始；首次 DNS/握手发生在窗口开始前，不计入。窗口内发生重连时，重连停顿仍计入连续墙钟窗口。

## 4. 故障注入

故障注入覆盖的范围和检查点在这张表里。

| 注入 | 测试方式 | 期望 |
|---|---|---|
| WebSocket 断开 | 本地 server 主动 `close()` | feed 退避重连；`on_disconnect/on_connect` 计数；数据缺口记录 |
| 消息停滞 | 本地 server 停止发送 > `stale_timeout_ms` | 连接被判定 stale 并重建 |
| depth 丢包 | 删除中间 `u` 序列 | `BookResult=gap`，缓冲，请求快照；快照后恢复同步 |
| 快照过旧 | 快照 `lastUpdateId` 落后于缓冲首事件 | 保持未同步并保留缓冲，等待新快照；不得输出因子 |
| 交叉簿 | 构造 bid ≥ ask 的增量 | 立即隐藏订单簿、计数并请求快照 |
| REST 500 | mock 返回 500 若干次后成功 | 指数退避重试；最终成功或健康降级 |
| WAL 损坏 | 翻转 payload 一个字节 | `WalReader` 抛 `WalCorruptionError`，`verify` 失败 |
| WAL 截断 | 截掉末尾一条记录的尾部 | 默认严格模式报错；允许模式记录 `truncated_tail_bytes` |
| 慢消费者 | 小队列 + 人工延迟 | 反压计数增加，原始帧不丢；处理滞后可见 |
| 磁盘写失败 | 单测 monkeypatch writer I/O | WAL 标记 error、后续 append 抛 `WalClosed`、进程可退出 |
| 派生文件关闭失败 | 集成测试 monkeypatch `JsonlSink.close` 抛 `OSError` | `derived_errors` 记录失败项，`derived_complete=false`，`clean_shutdown=false`，`verify` 失败 |

## 5. 对抗评审发现并修复的问题

实现做完以后，我让 AI 按接口和真实 WAL 逐模块找反例，自己复核。下面这些问题都是先复现、再修掉的，不是“看起来可能有问题”。

| 级别 | 模块 | 问题 | 修复 |
|---|---|---|---|
| major | 因子 | `_ofi_delta` 的 ask 侧价格变化符号与经典 Cont–Kukanov–Stoikov 定义相反；AI 生成的测试也沿用了同一个错误方向 | ask 下移 `-cur_qty`、上移 `+prev_qty`；修正接口文档与测试 |
| major | 订单簿 | 早先抓取的旧 REST 快照可能在较新的增量之后入队，`apply_snapshot` 会把簿回退到旧 `lastUpdateId`，下一笔连续增量被误判为 gap | `apply_snapshot` 拒绝 `lastUpdateId < last_update_id`，不重建、不回退；新增回归测试 |
| major | 接入 | `BinanceFeed.run()` 在握手刚完成时被取消，可能遗留一个未关闭的 WebSocket | 取消路径检查已完成握手的结果并 `shield` 关闭；补强取消测试 |
| minor | 执行 | 极大但有限的 price×1e8 溢出导致 `OverflowError`；名义上限的测试不变量在有价格变动时不可实现 | 缩放后检查有限性并丢弃；测试改为“不增加超限暴露 + 允许减仓” |
| minor | 指标/HTTP | `port=0` 重启复用了旧的临时端口；异常标签名可能碰撞 | 区分 configured/bound port 并恢复；指标边界问题记录为已知限制（生产标签为固定合法集合） |
| major | 关停/验证 | 派生 sink 的 `close()` 失败只写日志，`digests` 缺项但 `clean_shutdown` 仍可能为 true，留下不完整结果 | 关闭失败写入 `summary.derived_errors` 并把 `clean_shutdown` 置为 false；`derived_complete` 要求三项 digest 齐全；`verify` 同步 fail-closed；新增集成回归测试 |
| minor | 监控/健康 | `processing_lag_ms` 只用“最后到达帧 − 最后处理帧”，行情安静时即使队列头已等待很久也不会增长 | 增加 `oldest_pending_ms`，健康检查取两者较大值；补单测覆盖队列头等待场景 |

修完以后完整测试重跑通过（276 passed）。关停加固和健康指标修正在 3049 抽象对照之后、主结果 9821 之前完成：前者只改变失败路径的记账，后者只增加监控字段，成功路径的 WAL/derived 输出不变；9821 的 summary 包含新增的 `derived_complete`/`derived_errors`/`oldest_pending_ms` 字段，3049 已用新版 `verify` 复验通过。

## 6. 成交编号连续性（P2）

`@aggTrade` 的 `a` 编号现在按 symbol 单独检查。遇到重复或者回退的事件，计数后跳过，避免重复算进因子和模拟成交；遇到缺口，把 `missing_ids` 累加，缺口事件本身还是照常处理。这些统计写进 `summary.pipeline.trade_quality` 和 Prometheus 指标。

抽象做市性能基准那次运行的 388,394 条 WAL，运行期 `trade_quality` 计数器显示 6 个 symbol 都是 0 duplicates / 0 backwards / 0 gaps / 0 missing_ids；53b5 的完整证据在 Release，主结果 9821 的同类证据在 `运行材料/03_验证证据/成交编号完整性_最终版.json`。这里要分清两件事：`raw_frame_loss=0` 说的是程序没有漏收已经送达的 WebSocket 帧；`trade_gap=0` 只说明这段流里没检测到 aggTrade ID 缺口，证明不了断线期间交易所端没发生成交，断线造成的数据缺口还是单独记在 `summary.data_gaps` 里。

严格版 6db8 是另一组数：该次运行也有网络侧缺口，完整数字和边界见 `交付说明.md` §6。它同样只能证明收到的 272,784 个 WS 帧都落盘，不能证明交易所行情完整；公开 WS 不会自动补发，Binance 公共 REST `aggTrades` 可按 `fromId`/时间区间分页补取聚合成交，但本 demo 尚未实现 REST 补采，缺口记录在 `data_gaps`；历史 depth 增量和原 WS 帧不能按该方式恢复。

## 7. 实测结果

完整测试套件是 `276 passed, 0 failed`，Windows 11、Python 3.14.7。主结果现货 run `20261021T162501Z-9821` 通过了 `verify` 和 `replay --verify`（650,542 条 WAL，0 负仓位/0 负现金）；3049 抽象对照也通过了同一套 verify/replay。下面的 53b5 数据是历史性能基准，用来和旧验证证据对照。历史基准的正式实测窗口 900.116 s，6 个交易对，`run_id=20261020T072820Z-53b5`。窗口落在 07:00–08:00 UTC 这个小时桶；该窗口的成交额、笔数和排名在 Release 的 `market_activity.json` 里，本次提交不展开历史排名。

数量对账是这样的：原始帧 388,388，WAL 388,394（WS 388,388 加 snapshot 6），处理 388,394。丢失、未处理、未入队都是 0，`drained=true`，`clean_shutdown=true`。`verify` 返回 `ok=true`，388,394 条记录的 CRC 全部通过，两个分段的 SHA-256 和 manifest 对得上。回放的 factors、signals、fills 三个 SHA-256 跟运行目录里的 derived 一致，计数一致（53b5 的 derived 由同一份 WAL 重算）；Release 里的 53b5 `replay_summary.json` 是 21.439 s / 18,116.6 events/s；离线回放吞吐约为该窗口实时平均帧率的 42 倍，这是两种运行方式的速率比，不是实时容量证明。

`verify_run` 现在是 fail-closed：`summary.json` 和 `manifest.json` 必须存在且能解析，WAL 记录数必须大于 0，`clean_shutdown` 必须为 true，`digests` 必须包含 factors/signals/fills 三项且为字符串；如果 summary 显式写了 `derived_complete=false` 或非空 `derived_errors`，也直接失败。三个 derived 文件必须存在，重算出的 SHA-256 要同时与 `summary.digests` 和 `manifest.files` 对上，其他 manifest 文件也会逐个重算。空目录、损坏 summary、缺派生 digest、删掉或改过 derived 文件都会直接失败，不再返回 `ok=true`。

`replay` 默认写到独立的 `<run_id>-replay` 目录，目录非空会拒绝，不会覆盖原 `replay/` 证据；需要写输出目录的命令都显式带 `--out`。replay 还会重算运行目录 `derived/` 下三个文件的 SHA-256，不再只比较 `summary.json` 里的 digest，所以 derived 被改过时 replay 也会失败。

现货变体用同一份 53b5 WAL 重放，得到 3,077 fills，负仓位和负现金都是 0；独立现货采样的完整数据在 Release，本次邮件不展开。

健康语义这块，正式 summary 里 `health_before_shutdown.ok=true`、`health_final.ok=true`、`health_final_context=after_intentional_shutdown`，主动关停造成的 feed 断开不会再被误报成异常。处理滞后同时看 `processing_lag_ms` 和 `oldest_pending_ms`，取两者较大值判断，避免行情安静时队列头长时间等待被漏报。

### 7.1 严格落盘与异常终止

严格模式用 `config/spot_long_only_durable.toml`，`fsync_policy=always`，跑了 15 分钟：`run_id=20261020T082850Z-6db8`，272,784 帧、272,802 条 WAL，每条记录都 fsync；负仓位和负现金都是 0，`verify` 和 `replay --verify` 都通过。该次运行有网络侧缺口（见 `交付说明.md` §6）；重连的具体原因尚未隔离，不能唯一归因到 fsync。收到的原始帧一条没丢，订单簿 resync 后恢复；完整数据在 Release。

异常终止实验用 `tools/crash_recovery_check.py`：起一个短时 live，然后强制杀进程，不走优雅关闭。强杀后恢复读取 229 条有效记录，CRC 和 seq 连续，`truncated_tail_bytes=0`；当前证据没有保存可对账的 `durable_seq`/ACK，不能单凭它证明这 229 条都已完成 fsync。进程是被杀掉的，所以没有 `summary.json`，也没有 `clean_shutdown`，这符合预期。证据在 [异常终止恢复.json](../运行材料/03_验证证据/异常终止恢复.json)。该 JSON 是旧版工具输出，只包含 `wal.records`、`records_by_kind`、`truncated_tail_bytes`、`errors` 等字段，没有新版工具的 `killed_by_test` 等 checks；不要把新版工具的检查能力追认到这次旧结果。

这几个结论的边界要说清楚：异常终止测试验证的是“应用层强制终止后的 WAL 可读前缀”，不是物理掉电或系统崩溃恢复安全；工具不单独证明哪些记录达到了 `durable_seq`，也不验证恢复后能 replay 出完整的因子/信号/成交。`always` 是应用层每条 fsync，不等于对磁盘固件或者物理损坏有绝对保证；`interval` 的目标 250 ms 组提交不是硬上界，队列或者磁盘一积压，未同步窗口就会变大。

## 8. 测试的局限

测试也有够不到的地方。本地 mock 只能覆盖协议和状态机行为，真实交易所的撮合、限频细节、网络抖动它模拟不了。回放确定性证明的是“对这份 WAL 的输入，同一实现给出同一输出”，不是对任意未来输入的证明。单机测试没覆盖多进程/多机、时钟跳变、内核 OOM、磁盘满这些生产故障。Python 的 GC 停顿和操作系统调度还会进入延迟长尾，所以报告给的是分位数，不是只报一个均值。
