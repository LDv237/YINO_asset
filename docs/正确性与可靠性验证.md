# 正确性与可靠性验证

我把“能跑”拆成了六类可以重复的验证：单元正确性、状态机恢复、端到端链路、故障注入、确定性回放、完整性校验。下面所有命令都在项目根目录执行。

## 1. 验证矩阵

每一层看什么、证据在哪儿，都在这张表里。

| 层次 | 关注点 | 证据 |
|---|---|---|
| 单元测试 | 订单簿序列规则、WAL 格式/CRC、因子手算、策略风控、模拟撮合、指标并发 | `pytest` |
| 集成测试 | 本地模拟交易所（WebSocket + REST）→ 实时引擎 → WAL → 派生输出 → 回放 | `tests/test_integration_live.py` |
| 故障注入 | 断线重连、消息超时、REST 500/重试、WAL CRC 翻转、尾部截断、快照过旧/丢包、交叉簿 | 各模块测试中的 mock/fixture |
| 运行时对账 | 接收帧数 = WAL 记录数 = 已处理事件数；队列排空；无静默丢弃 | `summary.json.reconciliation` |
| 确定性回放 | 同一 WAL 回放产生的因子/信号/成交 SHA-256 与实时一致 | `replay_summary.json.comparison` |
| 完整性校验 | WAL magic/长度/CRC/seq、manifest 分段 SHA-256、产物校验和 | `python -m tickforge verify` |

## 2. 运行测试

装依赖、跑测试就两条命令：

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

结果 `272 passed, 0 failed`，环境是 Python 3.14.7、Windows 11。我另外起了一个全新的虚拟环境，只装 `requirements-dev-lock.txt`，`pip check` 没有冲突，272 个测试同样全过。

重点用例按文件过一遍：

- `tests/test_book.py`：覆盖 Binance 文档里“快照 `lastUpdateId` + 首笔 `U/u`”的边界，连续更新、重复、重叠、gap 进缓冲再由新快照恢复，快照过旧（缓冲首事件 `U > last+1`）时不能误判成同步，还有交叉簿、零量删除、`top_levels` 排序、缓冲溢出、`begin_resync`。另外有一个随机差分测试，同一事件流分别喂给实现和朴素全量簿，一步一步比对。
- `tests/test_wal.py`：10k 记录往返、分段轮转、CRC 篡改、尾部截断、fsync 策略、关闭/Digest；读取端严格校验 seq 单调和长度上限。
- `tests/test_factors.py`：microprice、spread 手算，OFI 四种最优档变化，成交不平衡，动量窗口；还有波动非负、节流/乱序时间、reset、无簿/单边簿。
- `tests/test_strategy.py` / `tests/test_simulator.py`：公允价、库存偏移方向、冷却、禁用以外的单边限制；买卖/部分成交、费率、平均成本、名义上限、取消、对账；相同输入跑两次，得到的 `Fill` 序列相同。
- `tests/test_feed.py` / `tests/test_rest.py`：本地 WebSocket 测消息接收/时间戳、断线重连、stale 超时；本地 REST 测成功、500 重试、重试耗尽、字段校验失败。
- `tests/test_metrics.py` / `tests/test_http.py`：多线程并发计数、直方图分位、Prometheus 文本、`/healthz` 200/503、`/metrics`。
- `tests/test_integration_live.py`：本地模拟 Binance，1 个交易对、2 秒窗口；验证 `clean_shutdown`、无丢失、订单簿同步、因子/信号/成交都非零；`verify_run` 通过，`ReplayRunner` 的摘要和实时运行一致。

## 3. 15 分钟实测的对账口径

`summary.json` 里是这么几组字段：

```json
{
  "counts": {"ws_frames_received": ..., "processed_envelopes": ...,
             "pipeline": {"ws_frames": ..., "snapshots": ..., "factor_snapshots": ...,
                          "signals": ..., "fills": ...}},
  "wal": {"records_ws": ..., "records_snapshot": ..., "records_total": ...},
  "reconciliation": {"lost_raw_frames": 0, "unprocessed_at_shutdown": 0,
                     "not_enqueued_at_shutdown": 0, "drained": true},
  "clean_shutdown": true
}
```

判定就按这六条来：

1. `ws_frames_received == wal.records_ws`：每个收到的原始帧都进了 WAL（正常关闭时 flush+fsync；`interval` 的崩溃窗口见 `docs/性能实测.md` 第 4 节的持久化契约）；
2. `wal.records_ws + wal.records_snapshot == processed_envelopes`：每个持久化事件都被处理；
3. `lost_raw_frames == 0`、`unprocessed_at_shutdown == 0`、`not_enqueued_at_shutdown == 0`；
4. `clean_shutdown == true`；
5. `verify` 通过；
6. `replay --verify` 的 `digests` 三项全部匹配。

统计窗口从第一条行情到达才开始，DNS、握手、重连这些时间都不算进 15 分钟。

## 4. 故障注入

故障注入覆盖的范围和检查点在这张表里。

| 注入 | 测试方式 | 期望 |
|---|---|---|
| WebSocket 断开 | 本地 server 主动 `close()` | feed 退避重连；`on_disconnect/on_connect` 计数；数据缺口记录 |
| 消息停滞 | 本地 server 停止发送 > `stale_timeout_ms` | 连接被判定 stale 并重建 |
| depth 丢包 | 删除中间 `u` 序列 | `BookResult=gap`，缓冲，请求快照；快照后恢复同步 |
| 快照过旧 | 快照 `lastUpdateId` 落后于缓冲首事件 | 保持未同步并保留缓冲，等待新快照；不得输出因子 |
| 交叉簿 | 构造 bid ≥ ask 的增量 | 立即隐藏订单簿、计数并请求快照 |
| REST 500 | mock 返回 500 若干次后成功 | 指数退避重试；最终成功或健康降级 |
| WAL 损坏 | 翻转 payload 一个字节 | `WalReader` 抛 `WalCorruptionError`，`verify` 失败 |
| WAL 截断 | 截掉末尾一条记录的尾部 | 默认严格模式报错；允许模式记录 `truncated_tail_bytes` |
| 慢消费者 | 小队列 + 人工延迟 | 反压计数增加，原始帧不丢；处理滞后可见 |
| 磁盘写失败 | 单测 monkeypatch writer I/O | WAL 标记 error、后续 append 抛 `WalClosed`、进程可退出 |

## 5. 对抗评审发现并修复的问题

实现做完以后，我让 AI 按接口和真实 WAL 逐模块找反例，自己复核。下面这些问题都是先复现、再修掉的，不是“看起来可能有问题”。

| 级别 | 模块 | 问题 | 修复 |
|---|---|---|---|
| major | 因子 | `_ofi_delta` 的 ask 侧价格变化符号与经典 Cont–Kukanov–Stoikov 定义相反；AI 生成的测试也沿用了同一个错误方向 | ask 下移 `-cur_qty`、上移 `+prev_qty`；修正接口文档与测试 |
| major | 订单簿 | 早先抓取的旧 REST 快照可能在较新的增量之后入队，`apply_snapshot` 会把簿回退到旧 `lastUpdateId`，下一笔连续增量被误判为 gap | `apply_snapshot` 拒绝 `lastUpdateId < last_update_id`，不重建、不回退；新增回归测试 |
| major | 接入 | `BinanceFeed.run()` 在握手刚完成时被取消，可能遗留一个未关闭的 WebSocket | 取消路径检查已完成握手的结果并 `shield` 关闭；补强取消测试 |
| minor | 执行 | 极大但有限的 price×1e8 溢出导致 `OverflowError`；名义上限的测试不变量在有价格变动时不可实现 | 缩放后检查有限性并丢弃；测试改为“不增加超限暴露 + 允许减仓” |
| minor | 指标/HTTP | `port=0` 重启复用了旧的临时端口；异常标签名可能碰撞 | 区分 configured/bound port 并恢复；指标边界问题记录为已知限制（生产标签为固定合法集合） |

修完以后完整测试重跑通过，又用真实行情 smoke 和回放把摘要重新对了一遍。

## 6. 成交编号连续性（P2）

`@aggTrade` 的 `a` 编号现在按 symbol 单独检查。遇到重复或者回退的事件，计数后跳过，避免重复算进因子和模拟成交；遇到缺口，把 `missing_ids` 累加，缺口事件本身还是照常处理。这些统计写进 `summary.pipeline.trade_quality` 和 Prometheus 指标。

抽象做市性能基准那次运行的 388,394 条 WAL，回放结果是 6 个 symbol 都是 0 duplicates / 0 backwards / 0 gaps / 0 missing_ids，证据在 `artifacts/evidence/trade_integrity.json`。这里要分清两件事：`raw_frame_loss=0` 说的是程序没有漏收已经送达的 WebSocket 帧；`trade_gap=0` 只说明这段流里没检测到 aggTrade ID 缺口，证明不了断线期间交易所端没发生成交，断线造成的数据缺口还是单独记在 `summary.data_gaps` 里。

严格版 6db8 是另一组数：2 次重连、2 段 data gap（1.151 s / 0.925 s）、12 次订单簿 gap / 12 次 resync、12 个 aggTrade 序列 gap，累计缺失 1,379 个 ID。它同样只能证明收到的 272,784 个 WS 帧都落盘，不能证明交易所行情完整；缺口期间的成交补不回来。

## 7. 实测结果

完整测试套件是 `272 passed, 0 failed`，Windows 11、Python 3.14.7。正式实测窗口 900.116 s，6 个交易对，`run_id=20261020T072820Z-53b5`。窗口落在 07:00–08:00 UTC 这个小时桶，成交额 73.96M USDT、125,770 笔，在 47 个完整小时里排 3/47，也就是 95.7 分位，见 `artifacts/evidence/market_activity.json`。

数量对账是这样的：原始帧 388,388，WAL 388,394（WS 388,388 加 snapshot 6），处理 388,394。丢失、未处理、未入队都是 0，`drained=true`，`clean_shutdown=true`。`verify` 返回 `ok=true`，388,394 条记录的 CRC 全部通过，两个分段的 SHA-256 和 manifest 对得上。回放的 factors、signals、fills 三个 SHA-256 跟实时运行一致，计数一致；交付的 `replay_summary.json` 是 16.428 s / 23,642.8 events/s，按这份摘要算带派生余量约 55 倍。

`verify_run` 现在是 fail-closed：`summary.json` 和 `manifest.json` 必须存在且能解析，WAL 记录数必须大于 0，`clean_shutdown` 必须为 true，并且会重算 `manifest.files` 的 SHA-256。空目录、损坏 summary、被改过的 derived 文件都会直接失败，不再返回 `ok=true`。

`replay` 默认写到独立的 `<run_id>-replay` 目录，目录非空会拒绝，不会覆盖原 `replay/` 证据；文档里的命令都显式带 `--out`。replay 还会重算 live `derived/` 下三个文件的 SHA-256，不再只比较 `summary.json` 里的 digest，所以 live derived 被改过时 replay 也会失败。

另外还有两组结果要提一下。第一轮 15 分钟跑了 443,326 帧，和评审期的磁盘压力重叠，结果还是 0 丢失、0 gap、0 重连，反压和落盘路径在压力下保持完整。现货只做多变体用同一份 WAL 重放，得到 3,081 fills，负仓位和负现金都是 0；另外独立跑了一次 15 分钟，325,280 帧、2,131 fills，负仓位和负现金同样是 0，回放摘要一致。

健康语义这块，正式 summary 里 `health_before_shutdown.ok=true`、`health_final.ok=true`、`health_final_context=after_intentional_shutdown`，主动关停造成的 feed 断开不会再被误报成异常。

### 7.1 严格落盘与异常终止

严格模式用 `config/spot_long_only_durable.toml`，`fsync_policy=always`，跑了 15 分钟：`run_id=20261020T082850Z-6db8`，272,784 帧、272,802 条 WAL，每条记录都 fsync；负仓位和负现金都是 0，`verify` 和 `replay --verify` 都通过。期间网络重连 2 次，造成 data gap，但收到的原始帧一条没丢，订单簿 resync 后恢复；这个小时桶（08:00–09:00 UTC）的成交额排名是 4/47，93.6 分位。

异常终止实验用 `tools/crash_recovery_check.py`：起一个短时 live，然后强制杀进程，不走优雅关闭。WAL 里 229 条已经 fsync 的记录全部可读，CRC 和 seq 连续，`truncated_tail_bytes=0`。进程是被杀掉的，所以没有 `summary.json`，也没有 `clean_shutdown`，这符合预期。证据在 [异常终止恢复.json](../交付材料/04_验证证据/异常终止恢复.json)。

这几个结论的边界要说清楚：异常终止测试验证的是“应用层强制终止后的 WAL 可读前缀”，不是物理掉电或系统崩溃恢复安全；工具不单独证明哪些记录达到了 `durable_seq`，也不验证恢复后能 replay 出完整的因子/信号/成交。`always` 是应用层每条 fsync，不等于对磁盘固件或者物理损坏有绝对保证；`interval` 的目标 250 ms 组提交不是硬上界，队列或者磁盘一积压，未同步窗口就会变大。

## 8. 测试的局限

测试也有够不到的地方。本地 mock 只能覆盖协议和状态机行为，真实交易所的撮合、限频细节、网络抖动它模拟不了。回放确定性证明的是“对这份 WAL 的输入，同一实现给出同一输出”，不是对任意未来输入的证明。单机测试没覆盖多进程/多机、时钟跳变、内核 OOM、磁盘满这些生产故障。Python 的 GC 停顿和操作系统调度还会进入延迟长尾，所以报告给的是分位数，不是只报一个均值。
