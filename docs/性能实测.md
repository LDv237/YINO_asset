## 2. 方法

计时不是从敲命令开始，而是进程启动、建连之后，收到第一条行情才开始。`--duration 900` 到点后请求停止，停止过程包括断开连接、排空队列、fsync、写摘要，这些时间都不算进窗口。

吞吐按三类数分别报：WAL 原始帧、`aggTrade`/depth 事件，以及派生出来的因子和信号。速率就是计数除以 `window_s`。

延迟的取点在每个 WebSocket 帧 `recv()` 返回之后，立刻读一次 `perf_counter_ns()`；`e2e` 是这一刻到该帧走完流水线的时间差。直方图用 1 µs 到 60 s 的固定对数桶，分位数报的是桶上界，偏保守，所以表里的值不会比真实值更好。

资源用 `psutil.Process().memory_info().rss` 和 `cpu_percent()` 每秒采一次，CPU 按单核百分比算，100% 就是一个逻辑核跑满。

丢没丢数据看 `reconciliation`：接收帧、WAL 记录、处理事件、队列剩余要能对上；`clean_shutdown` 还要求 `lost_raw_frames=0`，并且所有队列排空。确定性是跑完以后用同一份 WAL、同一份 `config.json` 再 replay 一遍，比对三个派生文件的 SHA-256。

## 4. fsync 策略对比

这里先把持久化的口径说清楚。正式性能基准用 `interval`，正常关闭会排空并 fsync，做到 0 丢失；但进程崩溃或者掉电时，没同步的尾部可能丢。250 ms 是尝试组提交的目标间隔，不是硬上界。要严格落盘就用 `always`，每条记录 fsync 完才继续处理；只追求吞吐的话，`never` 只能算基线。三种策略我都实测了。

同一数据源，每次只改 `fsync_policy`，分别跑 60 秒或 30 秒。

| 策略 | 记录数 | p50 e2e | p99 e2e | fsync 次数 | 说明 |
|---|---:|---:|---:|---:|---|
| `interval` 250 ms | 3,696 | 0.362 ms | 1.218 ms | 116 | 默认 |
| `always` | 3,509 | 2.048 ms | 4.871 ms | 3,510 | 每条 fsync 后才处理；应用层强持久性，非物理绝对保证 |
| `never` | 2,696 | 0.256 ms | 1.024 ms | 1 | 仅关闭/轮转时同步，吞吐基线 |

三次实验都是 30 s、只跑 BTCUSDT。行情活跃度不一样，记录数不能直接拿来比吞吐，但延迟按事件统计还是能比的。数据在 `artifacts/experiments/fsync/<policy>/runs/*/summary.json`。

`always` 把每个事件的端到端延迟抬高了大约一个数量级。它保证的是应用层每条记录都 fsync 过，不是物理介质上的绝对保证。`never` 延迟最低，可进程一被杀，尾部就没了。默认的 `interval` 是延迟和持久性之间的折中，真要严格口径就上 `always`。

### 4.2 完整性边界与取舍

| 模式 | 同步行为 | 正常关闭 | 崩溃/掉电 | 本交付证据 |
|---|---|---|---|---|
| `interval`（53b5） | 每 250 ms 尝试组提交 | 停止接收、排空队列、flush+fsync；0 丢失 | 未同步的尾部可能丢；250 ms 是目标间隔，不是硬上界 | 388,394 条 WAL，`lost_raw_frames=0`，`drained=true` |
| `always`（6db8） | 每条记录 fsync 后才进处理 | 0 丢失 | 应用层保证；不是对物理介质的绝对保证；异常终止后可读已 fsync 前缀 | 272,802 次 fsync，0 丢失；2 次重连、12 次 resync、1,379 个缺失 ID |
| `never` | 只在关闭/轮转时同步 | 0 丢失 | 崩溃窗口最大 | 只作吞吐基线，不用于正式数据 |

`interval` 没有逐条 fsync，不等于不符合题目：题目要的是同步策略、正常关闭的完整性和异常终止的边界都写清楚。正常关闭的完整性由排空 + flush + fsync 保证；崩溃窗口明确标注为“未同步尾部可能丢”，不是运行期静默丢帧。

严格版 6db8 的那次运行观察到 2 次重连、12 次 resync、1,379 个缺失 aggTrade ID；具体原因尚未隔离，不能唯一归因到 fsync。它没有丢已经收到的 WS 帧；缺口行情不会自动补发，本 demo 尚未实现 REST 补采。这是持久化优先的取舍，不否定 `interval` 版 53b5 已经完成的链路：53b5 是性能/延迟基准，6db8 是严格持久化合规证据，两者用途不同。

## 5. 回放和处理能力

15 分钟的 WAL 全量回放，连派生文件一起写，耗时 21.439 s，吞吐 18,116.6 events/s。实时平均 431.5 msg/s；离线回放吞吐约为该窗口实时平均帧率的 42 倍，这是两种运行方式的速率比，不是实时容量证明。纯处理用 `python -m tickforge bench --run <run_id> --repeat 3`，三次 29,044.1 / 29,380.8 / 30,583.4 events/s，按 30,583.4 / 431.5 约 71 倍，同样不能当成实时容量上界。

## 6. 解释与局限

这些数字得先交代口径。延迟是用户态处理延迟，不含交易所撮合、网络 RTT 和内核调度，所以不能拿去跟 colocation 或 HFT 的指标直接比。分位数是直方图桶上界，p99 这些数偏保守，`max` 里可能夹着一次 GC 或者调度抖动。整套东西跑在单机单进程上，没做 CPU 绑核、NUMA、内核旁路，也没上 FPGA；真实的 HFT 这些都要有。

成交这块用的是交易所的 `@aggTrade`，按 taker 订单聚合，不是 `@trade` 的逐笔 fill。原始 WAL 保存了完整 payload，包括 `f/l` 首尾成交编号，但组内每一笔的明细还原不出来。做成交量不平衡，用汇总的总量和方向够了；要看逐笔微观结构，得换到 `@trade`。

模拟撮合不排队，也不建模撤单延迟，算出来的收益没有意义。`Simulator` 还是个抽象记账器，允许负仓位、负现金，不代表 Binance 现货账户真能这么执行，借币、保证金、强平都没建模。这个项目只验证链路完整性。网络和交易所限频会随时间和地区变，复现的时候以 `summary.data_gaps` 和 `snapshot_errors` 为准。

## 7. 复现命令

复现按下面几条命令跑：

```bash
python -m tickforge live --config config/default.toml --duration 900 --out artifacts
RUN_DIR=$(ls -td artifacts/runs/* | head -1)
python -m tickforge verify --run "$RUN_DIR"
python -m tickforge replay --run "$RUN_DIR" --out "$RUN_DIR-replay" --verify
python -m tickforge bench --run "$RUN_DIR" --repeat 3
python tools/analyze_run.py "$RUN_DIR"
```
