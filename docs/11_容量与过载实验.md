# 容量与过载实验（组件级）

> 这份补充实验只回答“处理流水线能否承受观察到的 N 倍负载”，不是新的 live 主结果，也不回答“端到端 live 容量上限是多少”。

## 1. 目的与边界

主结果 9821 能证明 15 分钟真实行情窗口下的稳定性、处理延迟和正常关闭完整性，但没有证明容量上限或过载恢复。这次我只测**处理流水线**这一层：

- 输入：9821 的 650,542 条 WAL 记录（含 10 个快照），按原始平均接收速率 722.783 条/s 的 **2x / 5x** 重新节拍；
- 驱动：同一个 `Pipeline`、同一份 `config.json`，前面加一个容量 200,000 的有界队列；
- 记录：实际 offered/processed 速率、队列峰值、队列满等待次数、单事件处理时间 p50/p99/p999、signals/fills 是否与 live 一致、异常计数。

**不包含**：WebSocket 接收/网络 RTT、WAL 写线程与 fsync、派生 JSONL 写入、磁盘变慢、真实交易所过载。因此这里的结论只能是“处理阶段的容量余量”，不是端到端 live 容量证明。

## 2. 方法

`tools/capacity_probe.py` 读取 9821 的 WAL，按 `原始平均速率 × 倍率` 的节拍把每个 envelope 放入有界队列；单消费者调用同一个 `Pipeline.process()`；采样器每 50ms 记录队列深度。完整 650,542 条记录在 2x/5x 下各跑一遍，signals/fills 与 live summary 对账。

```bash
# 先解压主结果的 raw/derived；探针直接读 raw/ 下的 WAL
python scripts/extract_main_run.py 运行材料/01_主结果_现货_9821
python tools/capacity_probe.py \
  --run 运行材料/01_主结果_现货_9821 \
  --rates 2,5 \
  --out 运行材料/04_容量探针
```

2x 约 450 秒，5x 约 180 秒。结果 JSON 在 `运行材料/04_容量探针/`。

环境：Python 3.14.7，Windows 11，12 逻辑核；与主结果同一台机器。

## 4. 我的判断

- 这部分只证明：在这台机器、这份 WAL、这个配置下，处理阶段至少能跟上 5x 的观察负载；队列峰值只有上限的 0.27%，没有触发队列满等待；650,542 条全部处理，signals/fills 与 live 一致。加速没有丢事件，也没有改变确定性输出。
- 我没有测：5x 是不是上限（10x 没跑）；WebSocket/WAL 写线程/派生 I/O 是否也能跟上；磁盘变慢、强制断线、多 symbol 突发下的恢复。真实过载要把这些阶段一起压，并注入慢盘/断线，留给下一步。
- 这次没有改执行模型：这个实验只补性能边界，`Simulator` 的 crossing/maker 语义仍是抽象记账，边界见报告 §7 第 3 条。

## 5. 下一步（这次没做）

1. 用本地 WS/WAL 全链路驱动 5x/10x，把 WAL 写线程和派生 I/O 纳入；
2. 限速/小容量磁盘，测 WAL 反压和是否出现静默丢帧；
3. 5x 下强制断线 + depth gap，测重连、快照恢复和 replay 一致性；
4. 如果 10x 出现持续反压，记录边界，不再继续加负载。

我的验收标准：无静默丢帧、队列有界、恢复后 book 重新 synced、replay digest 仍一致。
