# 开发过程与问题记录

下面按时间顺序说我怎么把 TickForge 从最小链路做到可回放系统，重点是我在各阶段遇到的问题和对应修改；验证方法见第 4 节。

## 1. 起点：先跑通最小链路

最初的目标很直接：尽快确认三件事，行情能进来、能落盘、能出信号。所以先从单交易对、`@aggTrade` 单流开始，把连接、消息解析、WAL 写入和派生输出跑通。该阶段不涉及复杂策略，只验证链路是否打通。

链路打通后，功能逐步增加：`depth@100ms` 的全量订单簿、`bookTicker` 最优档、6 个 USDT 交易对（把 15 分钟窗口的负载提上来）、因子和做市信号、模拟成交，再往后是健康检查、Prometheus 指标和确定性回放。

## 2. 先冻结接口，再写实现

在扩大功能之前，我先把事件结构、WAL 二进制格式、模块签名、指标名，还有确定性和不丢数据这两条约束，写进了 `docs/02_接口与数据契约.md`。这样后面存储、订单簿、因子、策略/执行、接入、指标可以分开写，再按同一份契约拼起来。

这样做的好处是：每个模块能先单独测，不用等整条链路；出了问题也容易判断，到底是实现偏离了契约，还是契约本身要改。

## 3. 遇到的问题与修正

按时间顺序，主要问题如下。

### 3.1 主站不可达

最早我直连 `stream.binance.com`，连接失败。我先排查网络环境，测试了几个域名，确认 `data-stream.binance.vision` 可用后，改用币安行情专用的只读域名；该域名仍属同一交易所的公开行情入口，数据源未更换。网络问题排除后，才继续检查代码。

### 3.2 双生产者顺序竞态

早期设计里，快照任务和 WebSocket 回调都能分配 `seq`、写 WAL、进处理队列。队列一满，先分到序号的协程可能后入队，WAL 的物理顺序和处理顺序就对不上了。

修改方法是增加一个统一的 ingestion 锁，把 socket 和快照这两个生产者串起来；`seq` 统一在 WAL append 之前分配；队列满了就等待、反压，已经持久化的事件不能丢。另外补了一个“WAL 顺序等于处理顺序”的测试，回放时也校验摘要。

### 3.3 重连时的隐式状态重置

早期版本在 WebSocket 重连时会把所有订单簿和缓冲清空，再请求新快照。问题是这个状态转移没写进 WAL，回放时不会发生，live 和 replay 就可能对不上。

后来改成：重连只记一个 data gap，订单簿要不要重建，交给下一笔 depth 的 `U/u` 连续性来判断。没丢包就接着用，丢了就自然进缓冲、走快照恢复。这样 live 和 replay 走的是同一套状态机。

### 3.4 fsync 测试竞态

有一个测试曾在第一次定时 fsync 后断言 10 条记录全部 durable，当时 writer 仍在排队。后来改为等待写入序号，并增加显式的 `flush_and_sync()` 屏障。这样就不会把测试自己的调度问题当成实现的问题。

### 3.5 OFI 符号方向

实现和测试都把 ask 侧符号写反了（测试也沿用了错误方向，因此全部通过）；用独立参考模型和手算对照才发现，改成 ask 下移 `-cur_qty`、上移 `+prev_qty`，接口文档和测试一起改。完整说明见 `docs/04_正确性与可靠性验证.md` §5。

### 3.6 tick 精度

手写测试的期望值多加了三位零，由 `str_to_ticks` 的边界测试发现。这类错误难以通过人工检查发现，因此价格和数量的整数 tick 转换必须有独立用例。

### 3.7 旧快照回退订单簿

旧实现会用较老的 `lastUpdateId` 重建订单簿，导致下一笔连续增量被误判成 gap；改成 `apply_snapshot` 拒绝 `lastUpdateId < current_last_update_id`，不重建、不回退，并补回归测试。完整验证见 `docs/04_正确性与可靠性验证.md` §5。

### 3.8 严格落盘模式实测

`fsync_policy=always` 是每条记录 fsync 完才处理。15 分钟运行约处理 27 万帧，p50 约 3.4 ms，慢于 interval 模式；该次严格模式运行还观察到 2 次网络重连，具体原因尚未隔离，不能唯一归因到 fsync。这次实验让我确定：持久化语义要和性能指标一起报，不能只写“零丢失”。

## 4. 验证方法

验证分层：接口对照 → 单元/集成 → 真实行情 smoke → WAL 校验/回放摘要。测试矩阵、故障注入和每个修复的验证见 `docs/04_正确性与可靠性验证.md`，逐文件覆盖见 `tests/README.md`。15 分钟实测看丢失、队列排空、延迟分位、重连/快照计数和资源；回放比较 factors/signals/fills 三项 SHA-256；crash 实验只证明强杀后 229 条可读前缀，不证明每条都已完成 fsync。

## 5. 反思

经过本项目，我对“测试通过”这一结论比以往更为谨慎。测试只能覆盖其检查范围，不能替代规格对照，也不能替代真实行情与回放摘要。对“零丢失”同样需要区分场景：正常关闭、进程崩溃和物理掉电三者的保证并不相同，报告中必须分别说明。
