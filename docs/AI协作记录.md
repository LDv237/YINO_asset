# 与 AI 协作的记录

题目鼓励使用 AI，并要求说明如何在代码编写中交互协作、如何验证正确性。本文记录实际工作方式，而非事后包装的“AI 很厉害”。

## 1. 原则

1. **接口先冻结，代码后并行**：先写 `docs/接口设计.md`，把事件模型、WAL 二进制格式、订单簿状态机、因子定义、策略/模拟接口、指标名、确定性约束固定下来。没有接口就并行，只会得到六个互不兼容的实现。
2. **每个模块自带测试**：AI 交付的代码必须在本地跑通自己的测试；测试不是装饰，是可执行的规格。
3. **对抗评审**：实现完成后由独立 agent 按接口逐条寻找反例，重点看竞态、顺序、边界、资源泄漏、确定性，而不是代码风格。
4. **人工保留决策权**：数据源、语言、落盘语义、队列/反压、断线状态机、回放口径由人决定；AI 提供实现和备选方案。
5. **不信任未验证的 API 假设**：网络库/框架用法先用最小脚本验证，再写入系统。

## 2. 实际流程

```text
需求拆解
  → 写接口文档（人）
  → 并行实现：WAL / 订单簿 / 策略执行 / 接入 / 指标 HTTP（AI agents）
  → 因子模块（依赖订单簿，待其完成）
  → 集成层 + CLI + 回放（人 + AI 审阅）
  → 独立对抗评审（每个模块一个 reviewer agent）
  → 本地单元/集成测试、真实行情 smoke、15 分钟实测
  → 根据实测修复，更新文档
```

AI 的角色：

- 生成模块骨架、算法实现、测试用例、mock server；
- 在接口约束下独立完成一个文件集，避免多人同时改同一文件；
- 作为 reviewer 寻找实现者忽略的边界；
- 生成文档初稿，由人核对事实与数字。

人的角色：

- 判断题目真正要什么（完整性/可验证性 > 策略收益）；
- 选择数据源并实测网络可达性；
- 决定“原始帧先落盘”“快照作为事件”“重连由 U/u 判定”等架构；
- 审查 AI 的假设，运行真实数据与回放；
- 对最终报告中的每个数字负责。

## 3. 具体交互与纠错

### 3.1 数据源探测

先并行探测 Binance 主站、`data-api.binance.vision`、OKX、Bybit、Gate 等端点的可达性。主站/多数交易所在本机网络不可达，`data-stream.binance.vision` 可用。这个结果直接改变了默认配置，也避免了“程序连不上 = 代码有 bug”的误判。

### 3.2 顺序竞态

早期流水线允许 WebSocket 回调和快照 worker 各自分配 `seq` 并入队。队列满时，先分配 seq 的协程可能后入队，导致 WAL 顺序与处理顺序不一致，回放摘要就会漂移。

修复：加一把 ingestion 锁，串行化两个生产者；`seq` 在 WAL append 前分配；入队等待不再因为 `stopping` 提前丢弃；增加“WAL 顺序 = 处理顺序”的约束与回放对比测试。

### 3.3 重连的隐式状态

早期实现会在 WebSocket 重连时清空所有订单簿和缓冲，并立刻请求快照。这个状态转移没有写入 WAL，回放时不会发生，导致 live/replay 结果可能不同。

修复：重连只记录数据缺口；是否重建由下一笔 depth 的 `U/u` 连续性决定。无丢包时订单簿无缝续用，有丢包时正常进入缓冲/快照路径。这样 live 与 replay 的状态机完全一致。

### 3.4 因子符号方向

对抗评审发现 `_ofi_delta` 的 ask 侧价格变化符号与经典 Cont–Kukanov–Stoikov 定义相反：ask 下移（新增卖压）被记为正，ask 上移（卖档被移除）被记为负。实现者的单元测试把同一错误方向写成了期望值，所以测试全绿；评审用独立参考模型与真实 WAL 重放做了对照，确认 151/282 个快照的 OFI 值受影响，并给出了修正公式。

修复：ask 下移 → `-cur.ask_qty`，ask 上移 → `+prev.ask_qty`；同步修正接口文档、实现 docstring 与测试期望。这个例子说明**测试通过与规格正确是两件事**，实现者和测试需要由不同视角审查。

### 3.5 其他被评审抓住的问题

- **旧快照回退订单簿**：REST 快照可能在较新的增量之后才入队（网络延迟 + 摄入锁竞争）。原实现会用旧 `lastUpdateId` 重建订单簿，下一笔连续增量被误判为 gap。修复为：快照的 `lastUpdateId` 小于当前值时直接忽略，不重建、不回退，并加回归测试。
- **握手完成窗口的取消泄漏**：`BinanceFeed.run()` 在 `websockets.connect()` 刚返回、尚未进入读循环时被取消，可能遗留未关闭的 TCP/TLS 连接。修复取消路径：检查已完成的 connect task、取回连接并 `shield` 关闭。
- **模拟器的名义上限测试不变量错误**：价格变动后，“每次成交后 |position|*price ≤ cap” 不可实现；实现本身只保证“不增加超限暴露、允许减仓”。修正测试与文档，并补上溢出处理。

### 3.6 测试自身的错误

- `test_normalize` 里手算 tick 期望值多写了三个零，测试立即失败，说明实现是对的、测试是错的；
- WAL 的 interval fsync 测试在第一次定时同步后就断言 10 条全部 durable，实际 writer 仍在排队。改为等待写入序号 + 显式 `flush_and_sync()` 屏障。

这两次都说明：**AI 写的测试也可能错**，失败时先判断是实现错还是测试错，不能为了让测试变绿而改实现。

### 3.5 公共 API 的版本差异

websockets 17 的 handler 签名、aiohttp 的 runner 生命周期、`asyncio` 在 Windows 上的信号处理，都先用最小脚本验证，再写入生产代码。AI 记忆中的旧版 API 不能直接采信。

## 4. 验证 AI 产出的方法

1. **规格对照**：逐条对照 `docs/接口设计.md` 的签名、返回状态、错误语义；评审者只报可复现的偏差。
2. **单元测试**：数学用手算、状态机用文档示例 + 随机对拍、WAL 用字节级往返/篡改/截断。
3. **集成测试**：本地模拟交易所跑完整链路（连接 → WAL → 同步 → 因子 → 信号 → 成交 → 关停 → 校验 → 回放）。
4. **真实数据 smoke**：短时间连接 Binance，验证解析、快照、订单簿同步和健康检查，而不是只依赖 mock。
5. **15 分钟实测**：检查丢失=0、队列排空、延迟分位、重连/快照计数。
6. **回放摘要**：三个 SHA-256 + 计数 + WAL 计数全部一致，才算“可复现”。

## 5. 哪些事不交给 AI

- 最终架构与验收口径；
- 对“没有丢数据”的确认（必须看对账与 WAL 校验）；
- 对实测数字的解释（延迟是否合理、是否被 GC/网络污染）；
- 公开仓库/邮件/附件等对外动作；
- 任何需要账号凭据的操作。

## 6. 反思

AI 显著加快了实现与测试覆盖，但它会**自信地给出错误假设**（旧 API、错误的测试期望、忽略并发顺序）。有效的协作方式不是“少用 AI”，而是：

- 把约束写成可执行的测试，而不是口头要求；
- 让实现者与评审者分离；
- 用真实数据和回放摘要做最终裁决；
- 人保留对系统语义与对外交付的责任。

最终测试与实测结果见 `docs/正确性与可靠性验证.md` 与 `docs/性能实测.md`。
