## 2. 方法

计时起点是进程启动、建连完成并收到第一条行情之后；执行命令的时刻不计入。窗口内发生重连时，重连停顿仍计入连续墙钟窗口。`--duration 900` 到点后请求停止，停止过程包括断开连接、排空队列、fsync、写摘要，这些时间都不算进窗口。

吞吐按三类数分别报：WAL 原始帧、`aggTrade`/depth 事件，以及派生出来的因子和信号。速率就是计数除以 `window_s`。

延迟的取点在每个 WebSocket 帧 `recv()` 返回之后，立刻读一次 `perf_counter_ns()`；`e2e` 是这一刻到该帧走完流水线的时间差。直方图用 1 µs 到 60 s 的固定对数桶，分位数报的是桶上界，偏保守，所以表里的值不会比真实值更好。

资源用 `psutil.Process().memory_info().rss` 和 `cpu_percent()` 每秒采一次，CPU 按单核百分比算，100% 就是一个逻辑核跑满。

数据完整性由 `reconciliation` 判定：接收帧、WAL 记录、处理事件和队列剩余必须一致；`clean_shutdown` 还要求 `lost_raw_frames=0`，并且所有队列排空。确定性验证是在运行结束后用同一份 WAL、同一份 `config.json` 再 replay 一遍，比对三个派生文件的 SHA-256。

## 3. 主结果 9821（现货）

`run_id=20261021T162501Z-9821`，900.037 s，日志/信号/成交/性能/回放全部来自同一次 live，没有混入重算结果。

| 指标 | 值 |
|---|---:|
| 原始帧 / WAL 记录 | 650,532 / 650,542（10 个快照） |
| 信号 / fills | 47,127 / 6,437 |
| depth / aggTrade / bookTicker | 47,830 / 43,593 / 559,109 |
| depth e2e p50 / p95 / p99 / p999 | 0.609 / 1.722 / 2.896 / 4.871 ms |
| 聚合 e2e p50 / p99 / p999 | 0.724 / 2.435 / 5.793 ms |
| 原始帧丢失 / `clean_shutdown` | 0 / true |
| data gap / 订单簿 resync | 0 / 0 |
| 负仓位 / 负现金 | 0 / 0 |
| `wal_queue_max` / `pipeline_queue_max` | 735 / 16 |
| recv→fsync p50 / p95（批次） | 262.1 / 311.7 ms |
| RSS 峰值 / CPU 平均 | 80.59 MiB / 15.10%（单核口径） |
| 回放 | `verified=true`、`deterministic=true`，三项 SHA-256 一致 |

解读这些指标时需要注意两点：

- **聚合 e2e 被 bookTicker 主导**。650,532 个帧里 559,109 个是 bookTicker（86.0%），经过接收、WAL、处理队列和解析后跳过订单簿→因子→策略→执行；订单簿→因子→报价的核心处理路径看 depth 行（p99 2.896 ms），模拟成交记账由后续 aggTrade 触发；聚合 p99 不代表完整交易链的 p99。
- **本地处理延迟不等于行情新鲜度**。计时从 `ws.recv()` 返回后才开始，不包含 WebSocket 库、TCP/内核缓冲和网络 RTT。毫秒级 e2e 只能证明接收后的处理表现；行情从交易所产生到策略完成还要加上网络和时钟偏差。

**这些数字证明什么**：本次实验验证了真实混合行情负载下连续 15 分钟的运行稳定性、正常关闭后的数据完整性及处理延迟。平均接收约 723 帧/s，其中约 86% 为轻处理的 bookTicker；depth 核心路径 p99 为 2.896 ms。该结果不代表持续容量上限或生产级 HFT 性能；本次真实采样未触发 WAL/处理队列反压，也没有重连，这证明该窗口运行顺畅，不证明容量上限或过载恢复能力（故障注入测试单独覆盖那些路径）。处理延迟从 `ws.recv()` 返回开始计时，不包含此前的网络及缓冲时间，也不能代表 fsync 持久化延迟（后者单独统计为 262/312 ms）。

补充：组件级容量探针（2x/5x，完整 WAL）见 `docs/11_容量与过载实验.md`；5x 下队列峰值 539/200,000、无反压、signals/fills 与 live 一致；仍不含 WAL/网络/派生 I/O，不是端到端容量证明。

## 5. fsync 策略对比

同一数据源，每次只改 `fsync_policy`，分别跑 30 秒、只跑 BTCUSDT。

| 策略 | WS 帧 / WAL 记录 | p50 e2e | p99 e2e | fsync 次数 | 说明 |
|---|---:|---:|---:|---:|---|
| `interval` 250 ms | 3,696 / 3,697 | 0.362 ms | 1.218 ms | 116 | 默认 |
| `always` | 3,509 / 3,510 | 2.048 ms | 4.871 ms | 3,510 | 每条记录 fsync 后才处理；应用层强持久性，非物理绝对保证 |
| `never` | 2,696 / 2,697 | 0.256 ms | 1.024 ms | 1 | 仅关闭/轮转时同步，吞吐基线 |

三次实验的行情活跃度不同，记录数不宜直接用于吞吐对比；延迟按事件统计，仍可比较。原始 summary 在 Release 的完整 artifacts 里。

## 6. 解释与局限

以下数字需先说明统计口径。延迟为用户态处理延迟，不含交易所撮合、网络 RTT 和内核调度，不能直接与 colocation 或 HFT 指标比较。分位数为直方图桶上界，p99 偏保守，`max` 可能包含一次 GC 或调度抖动。系统运行在单机单进程上，未做 CPU 绑核、NUMA、内核旁路，也未使用 FPGA 加速。

成交数据来自交易所的 `@aggTrade`，按 taker 订单聚合，与 `@trade` 的逐笔 fill 不同。原始 WAL 保存了完整 payload，包括 `f/l` 首尾成交编号，但无法还原组内每一笔的明细。

模拟撮合不排队，也不建模撤单延迟，模拟收益不具备解释力。主结果用现货配置，所有 position/cash ≥ 0，但仍是抽象记账器；3049 抽象对照允许负仓位/负现金。

## 7. 复现命令

提交包内主结果需先解压，再执行以下命令：

```bash
python scripts/extract_main_run.py 运行材料/01_主结果_现货_9821
python -m tickforge verify --run 运行材料/01_主结果_现货_9821
python -m tickforge replay --run 运行材料/01_主结果_现货_9821 \
  --out 运行材料/01_主结果_现货_9821-replay --verify
python -m tickforge bench --run 运行材料/01_主结果_现货_9821 --repeat 3
python tools/analyze_run.py 运行材料/01_主结果_现货_9821
```

离线样本：

```bash
python -m tickforge replay --run samples/demo_run --out samples/demo_run-replay --verify
```
